## Release gate — before any public tag / Etiketten önce kalite kapısı

1. Select the **exact main commit** and record the release's source SHA.
2. Resolve/merge the offline ZIP packaging PR **only if** its current commit passes full Python 3.11/3.12/3.13 and Chromium CI, offline-asset allowlist and `verify_release_readiness`. Never advertise an unmerged feature.
3. Build **real downloadable ZIP asset** from precisely the staged fictional public files. Inspect file list for personal information, unlisted files, private source, hotel records, symlinks and unsafe external dependencies; confirm `index.html` loads offline. Record the ZIP SHA-256.
4. Create a clearly named **demo** tag and GitHub Release **with the ZIP attached as a release asset**. Do not rely only on autogenerated source archives: those are different from a user-facing, byte-verified product bundle.
5. Include release notes: supported features, sample data, tested commit, known limitations, 10-language draft status, no live PMS/OTA/KBS/payments/AI/check-in, install instructions, source evidence, and issue reporting.
6. Confirm the release page and asset are publicly accessible; retain GitHub Actions build provenance and original release evidence.

**Publication needs an explicit release decision** because it affects external downloads and permanently published version identity. This document does not authorize automatic release/publishing.

## Metrics — what is and isn't measured / İndirme metrikleri

- **GitHub Release binary asset downloads:** GitHub REST release assets expose a `download_count` for attached assets. Report the asset name and date range, avoid merging counts of different assets or equating downloads with unique humans. Example evidence: `GET /repos/erenariel/konaklamaflow/releases/{release_id}/assets`. The generated source .zip/.tar.gz is **not the same** as a custom attached offline demo ZIP.
- **PyPI download events:** PyPI provides public BigQuery usage data; tools such as [PyPI Stats](https://pypistats.org/) can show daily/monthly download events. Mirroring, CI automation and retransfers complicate interpretation. Do **not** call these unique users or validated hotel adoption.
- **Real adoption:** stronger evidence comes from voluntary third-party demo trials, independent issue reports, concrete code contributions, and independently attributable repeat usage — all using fictional records and consent.
- **Avoid gaming metrics:** No deliberate self-download campaigns, bot-download inflation, manufactured reviews or unsupported claims of active installations.

References: [GitHub REST releases](https://docs.github.com/en/rest/releases/releases), [GitHub release assets](https://docs.github.com/en/rest/releases/assets), [PyPI statistics](https://docs.pypi.org/about/pypi-statistics/), [PyPI Stats methodology](https://pypistats.org/faqs).

## PyPI delivery policy / PyPI güvenli yayımlama

1. Confirm whether `konaklamaflow` exists on PyPI and whether the legitimate project owner controls the namespace. **PyPI ownership/status has not been verified by this document.**
2. Verify `pyproject.toml`, built **sdist and wheel**, project links, license, package data, README, entrypoints and a clean `pip install` run. Align the release version and Python runtime metadata; do not set `0.5.0` merely to match a UI version.
3. Prefer an isolated **Trusted Publishing (OIDC)** GitHub Actions workflow with minimum `id-token: write` job permission, a restricted PyPI environment and project-owner-controlled publisher setup. Never store long-lived tokens in the repository; the workflow must not run publishing from untrusted pull requests.
4. Optionally test with TestPyPI. Before production publish, obtain explicit maintainer release authorization and confirm the version isn't already occupied; PyPI files are not a safe place for experimental uploads.
5. Publish only after verification, record the package version, link and upload result, and only then add a truthful PyPI badge or installation instructions to the root README.

References: [PyPI Trusted Publishers](https://docs.pypi.org/trusted-publishers/), [GitHub Actions publisher setup](https://docs.pypi.org/trusted-publishers/using-a-publisher/), [Python package versioning](https://packaging.python.org/en/latest/discussions/versioning/).
